==================================================
P0 — MISSION AUTHORITY MONOTONICITY
==================================================

Fix the three supplied failing tests first.

Principle:

LLM semantic authority should be strong, but user-delegated authority must be monotonic.

A model may:
- understand semantic references;
- infer preference meaning;
- distinguish "must keep", "may cancel", "prefer", "avoid";
- resolve ambiguous intent with server grounding.

A model must not:
- increase an explicit numeric spending/loss/drift cap;
- erase a clearly protected Activity because of a conflicting model draft;
- silently drop unresolved references.

Implement an explicit merge model such as:

RawTextAuthorityEvidence
+ ModelMissionIntent
+ ServerEntityResolution
+ GlobalDelegationPolicy
= ResolvedMissionAuthority

Rules:
- explicit raw-text cap is a ceiling;
- global policy is a ceiling;
- resolved mission uses the most restrictive explicit authority ceiling;
- explicit local polarity beats a conflicting model guess;
- where raw text is genuinely ambiguous, model semantics may decide;
- unresolved references persist and grant no authority.

Do not make AI passive.

P1 — CITY SIGNAL PIPELINE
==================================================

Create a real server-owned sensing layer.

Suggested concepts:

CitySignal
ProviderObservation
IncidentFingerprint
JourneyRiskObservation
GuardianPulse

Weather:
reuse the existing Open-Meteo runtime. It already creates provider-verified WEATHER Events.

Mobility:
add a near-term mobility watcher:
- capture frozen travel estimates for upcoming legs;
- compare current provider estimates to the active-plan baseline / prior snapshot;
- derive TRAFFIC_DELAY only when a meaningful threshold is crossed;
- persist provider provenance and captured time;
- do not call live providers inside GET projections or deterministic feasibility.

A provider refresh must not directly mutate a Plan.
It creates trusted observations/events only.

Support:
- live provider mode;
- deterministic demo/simulation provider mode through the exact same ingestion contract.

==================================================
P2 — GUARDIAN PULSE / SCHEDULER
==================================================

The current `/guardian/scan` endpoint can remain as an explicit admin/debug trigger.

Add a real autonomous pulse mechanism.

Preferred low-complexity design:
- a separate Guardian worker process or a carefully controlled scheduler;
- no Celery/Kafka/Redis unless genuinely necessary;
- APScheduler is acceptable;
- one DB session per pulse;
- scan only ACTIVE Journeys with an ACTIVE standing mission;
- configurable interval;
- default disabled in tests unless explicitly enabled;
- deterministic test clock.

Suggested environment:
CITYNEXUS_GUARDIAN_AUTORUN=false
CITYNEXUS_GUARDIAN_INTERVAL_SECONDS=60

Do not create duplicate schedulers under Uvicorn reload.

The worker should:
refresh provider signals
→ persist observations/events
→ calculate incident identity
→ invoke Guardian
→ persist result

==================================================
P7 — FLAGSHIP ZERO-TOUCH E2E
==================================================

This is the V5 completion gate.

The browser must NOT click a "Run Guardian" button.

Scenario:

1. Create/start Journey.
2. Set standing mission and Autonomous mode.
3. Start Guardian worker/pulse.
4. Provider fixture initially reports normal conditions.
5. Fixture transitions to heavy rain + route delay.
6. Signal pipeline persists trusted evidence automatically.
7. Guardian wakes automatically.
8. Configured Agent runtime reasons over the incident.
9. Agent requests/reviews a CP-SAT V2 recovery.
10. Policy returns ALLOW_AUTO for an in-envelope option.
11. Active PlanVersion changes.
12. Protected cruise/dinner/C4 remain.
13. Control Tower receives live persisted operation events.
14. MapLibre updates before/after route.
15. Browser reload restores the exact domain truth.
16. Repeated same provider signal creates no duplicate recovery.

Negative:
- provider signal clears before action -> no stale mutation;
- over budget -> approval required;
- protected activity would be harmed -> block / stronger authority;
- provider outage -> degrade safely;
- model runtime unavailable -> deterministic Guardian fallback still works.
